# moodle-aws-iac

Infrastructure-as-code for a containerized [Moodle](https://moodle.org/) e-learning
platform on AWS — built as a personal portfolio project to practice and
demonstrate modular Terraform, container image supply chain (build → scan →
push), and CI/CD automation end to end.

> **Note on origin:** this repository reproduces a common Moodle-on-AWS
> deployment pattern from scratch, for learning and portfolio purposes. It is
> not derived from, and contains no code, credentials or documentation from,
> any client or employer project.

## Architecture

```
Internet
   │
   ▼
┌─────────────────────────┐
│  Application Load        │  (public subnets)
│  Balancer  :80/:443      │
└──────────┬───────────────┘
           │
           ▼
┌─────────────────────────┐        ┌──────────────────────┐
│  ECS Fargate service      │──────▶│  Amazon ECR            │
│  (Moodle container :8080) │        │  moodle image          │
│  private subnets          │        └──────────────────────┘
└──────────┬───────────────┘
           │
           ▼
┌─────────────────────────┐
│  RDS for MySQL             │  (private subnets, no public access)
│  credentials in Secrets    │
│  Manager, injected at      │
│  container startup         │
└─────────────────────────┘
```

All resources live inside a dedicated VPC with public subnets (ALB, NAT
gateway) and private subnets (ECS tasks, RDS) — the database and application
containers are never directly reachable from the internet.

## Stack

- **Terraform** (modular: `network`, `alb`, `ecs`, `ecr`, `rds` under
  [`terraform/modules`](terraform/modules), wired together per environment
  under [`terraform/environments`](terraform/environments))
- **AWS**: VPC, ALB, ECS Fargate, ECR, RDS for MySQL, Secrets Manager,
  CloudWatch Logs, IAM
- **Docker**: multi-stage build (`docker/Dockerfile`) — a throwaway stage
  fetches and unpacks Moodle, the runtime stage ships only `php:8.2-apache`
  plus the application code, with no build tools in the final image
- **GitHub Actions**: one pipeline for `terraform fmt`/`validate`/`plan`/
  `apply` (OIDC auth to AWS, no static keys, manual approval gate before
  `apply`), and a separate pipeline that builds, vulnerability-scans
  (Trivy), and pushes the Moodle image, then forces a new ECS deployment

## Why these design decisions

- **Modular Terraform, not one big file.** Each concern (network, load
  balancer, compute, registry, database) is its own reusable module with
  explicit inputs/outputs, wired together in
  [`terraform/environments/dev/main.tf`](terraform/environments/dev/main.tf).
  This mirrors how I've structured Terraform on real client engagements.
- **No secrets in the container image or in `config.php`.** Database
  credentials are generated by Terraform (`random_password`), stored in
  Secrets Manager, and injected into the ECS task at runtime via the task
  definition's `secrets` block — never baked into the image or committed to
  this repository.
- **Immutable image tags + vulnerability scanning before push.** The ECR
  repository is `IMMUTABLE`, and the build pipeline fails on HIGH/CRITICAL
  CVEs via Trivy before an image is ever pushed.
- **`apply` requires a manual trigger**, gated behind a GitHub Environment
  approval. `plan` runs automatically on every pull request so the diff is
  visible in review — `apply` never runs unattended, to avoid accidentally
  provisioning real AWS spend on a personal AWS account.
- **A dedicated security group per tier** (ALB, ECS service, RDS), each only
  allowing the minimum inbound traffic from the tier in front of it.

## Repository layout

```
.
├── docker/                  # Dockerfile, entrypoint, minimal config.php
├── terraform/
│   ├── modules/
│   │   ├── network/         # VPC, public/private subnets, NAT, routing
│   │   ├── alb/              # Application Load Balancer + target group
│   │   ├── ecs/               # Fargate cluster, task definition, service
│   │   ├── ecr/               # Container registry + lifecycle policy
│   │   └── rds/               # MySQL instance + Secrets Manager credentials
│   └── environments/
│       └── dev/               # Wires the modules together for one environment
└── .github/workflows/
    ├── terraform.yml         # fmt / validate / plan / manual apply
    └── docker-build.yml      # build → scan → push → force new deployment
```

## Running it yourself

1. Configure AWS credentials locally (or set up the OIDC role referenced in
   the workflows for CI).
2. Build and push an initial image so the ECS service has something to pull:
   ```bash
   cd docker && docker build -t <your-ecr-repo>:latest .
   ```
3. Provision the infrastructure:
   ```bash
   cd terraform/environments/dev
   terraform init
   terraform plan
   terraform apply
   ```
4. The Moodle URL is printed as a Terraform output (`moodle_url`). First load
   will take a minute while the ECS task pulls the image and the entrypoint
   waits for RDS to accept connections.

## What I'd change for a production environment

This is intentionally sized as a portfolio/dev project (single NAT gateway,
single-AZ RDS, no HTTPS listener). For production I'd add: one NAT gateway
per AZ, RDS Multi-AZ, an ACM certificate + HTTPS listener on the ALB with an
HTTP→HTTPS redirect, and a remote Terraform state backend (S3 + DynamoDB
lock table — already scaffolded, commented out, in
[`terraform/environments/dev/versions.tf`](terraform/environments/dev/versions.tf)).
